# Message 模块架构 QA

## QA-001：为什么需要 `Message`，而不是一直使用 `dict`？

### 设计动机

`Message` 为框架内部提供统一的数据模型，减少字典形状不一致的问题，并可以保存时间戳、元数据等内部信息。通过 `to_dict()`，内部对象再转换为外部模型 API 所需的字段。

```text
框架内部：Message（结构丰富、约束明确）
模型 API：dict（格式兼容、字段精简）
```

### 代价与生产方向

对象封装增加了复杂度，转换也需要维护。生产框架还需考虑消息版本、序列化兼容性、敏感信息脱敏、追踪 ID、工具调用和多供应商协议适配。

## QA-002：为什么 `role` 使用 `Literal`？

```python
MessageRole = Literal["user", "assistant", "system", "tool"]
```

`Literal` 本身主要是类型标注，帮助静态检查；配合 Pydantic 后还会进行运行时校验。它能减少拼写错误并明确允许的角色集合，但固定角色也会降低对第三方协议的扩展性。生产系统可以区分内部角色和供应商角色，通过适配器映射。

## QA-003：为什么时间戳默认生成，同时允许显式传入？

默认生成减少调用方负担；显式传入则支持历史恢复、消息重放、数据导入和确定性测试。应使用 `default_factory`，避免在类加载时只计算一次默认时间。

教学代码使用本地时间来突出默认值概念；生产系统应明确时间语义，通常使用带时区的 UTC 时间，并考虑时钟漂移、事件排序和重放幂等性。

## QA-004：为什么 `to_dict()` 不发送所有内部字段？

内部字段可能导致协议错误、隐私泄露、语义混乱、供应商耦合和额外 token 成本。因此教学实现显式只发送 `role` 和 `content`。生产系统应在供应商适配器中显式映射允许外发的字段，并对敏感 metadata 做脱敏。

## QA-005：为什么继承 Pydantic `BaseModel`？

`BaseModel` 同时提供类型驱动的字段模型、运行时校验、对象构造、序列化和统一错误处理，避免框架重复实现这些机制。生产系统还需考虑严格模式、版本迁移、序列化兼容性和性能成本。

## QA-006：为什么 `timestamp` 和 `metadata` 的可选性写法不完全一致？

文档使用 `timestamp: datetime = None` 表达“初始化时自动补时间”，但类型标注与默认值不完全一致；`metadata: Optional[Dict[str, Any]] = None` 则明确允许 `None`。教学阶段保留源码写法，模块复盘时再统一字段语义、时区和可变默认值策略。

## QA-007：为什么核心字段显式声明，可选字段通过 `**kwargs` 传入？

这样可以突出 `content`、`role` 是核心字段，`timestamp`、`metadata` 是附加字段。但 `**kwargs` 隐藏了允许的可选字段，拼写错误也不易发现。教学阶段保留该写法，生产 API 更适合显式声明可选字段。
